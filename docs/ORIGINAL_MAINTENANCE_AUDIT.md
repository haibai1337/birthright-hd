# Original Maintenance / Realm Management Phase Audit

## Scope and evidence

This is a research-only reconstruction from the original CD help (`RULES.TXT`), the cached `fire-lizard/birthrt` C++ source, and the existing Birthright HD engine and interface. The cached source is a later modified branch, not proof of unmodified retail behavior; source-only details are marked accordingly. The supplied original Maintenance screenshot is the visual reference for the parchment-left / active-map-right composition. No original executable was run, and no assets were changed.

Evidence labels:

- **Confirmed manual behavior**: stated in the recovered CD `RULES.TXT`.
- **Source-supported**: implemented in cached original source; retail equivalence is not proven.
- **HD policy**: deliberate current-project rule, not attributed to the original.
- **Unresolved**: evidence is missing, conflicts, or needs a retail/executable comparison.

## Original turn flow

```text
Complete the third Domain Action
  -> seasonal/domain-turn boundary processing
  -> automatic Advisors' Reports / Council hub
  -> player dismisses the hub
  -> random events and NPC realm administration
  -> Realm Management (not shown in Basic)
       Taxation / Occupation / Payroll / Maintenance / Reports
       make administrative choices (not Domain Actions) and review projections
       Collect Taxes (one action; computer resolves the province list)
       Select Actions (the interface changes to the Domain Actions screen)
  -> three Domain Actions for the new three-month Domain Turn
```

The CD help says Realm Management and Reports happen at the beginning of the first month; after the advisors, the Realm Maintenance screen appears on the left with the Anuire map on the right. Taxes are set and collected before the Domain Actions screen. The exact report/event/NPC order follows the source-traced sequence in [the Council UI flow investigation](./ORIGINAL_COUNCIL_UI_FLOW.md): the Council hub is dismissed before `RandomEvents()` and `DoNPCAdmin()`, then player management begins. The source's end-of-turn work and mode transition are in [`GAMEMAP.CPP::UpdateDataArea`](../reference/research-cache/fire-lizard-birthrt/GAMEMAP.CPP#L4316) and the post-report path near [the `DoNPCAdmin()` call](../reference/research-cache/fire-lizard-birthrt/GAMEMAP.CPP#L4791).

Realm Management is not a fourth Domain Action. It is the pre-action phase for reviewing and setting realm finances; after taxes are collected, the player explicitly selects Actions. A separate optional control can spend RP to increase bloodline strength; it does not replace one of the three action selections.

### Calculation qualifications

- The original tax table's displayed ranges are confirmed by the CD help. The cached tax and holding dice tables are source-supported; exact random outcomes are not reconstructed by using the midpoint. Port evidence conflicts: the help says half-level for all ports, while the cached source and statically inspected executable branch differ; the inspected binary was not run through a seasonal turn.
- Law-claim wording in the manual is high-level; the cached implementation's suspicious conditional means the precise per-target allocation remains unresolved.
- The cached source is explicit about the maintenance formula, class-sensitive regency, and native treasury tenths. Do not convert the above into a claim that every detail has been verified in an unmodified retail executable.
- The original help states that economic controls are automatic in Basic, but this audit does not establish the exact Basic-mode tax/expense result for all situations.

## Maintenance screen and interactions

### Composition and table

The original screen is a **parchment/data pane on the left and active Anuire strategic map on the right**. This is stated in CD help and shown by the supplied screenshot. The map remains available for strategic inspection; the help confirms right-click inspection of provinces, holdings and assets. No evidence found here proves that clicking a map province selects or scrolls its corresponding table row.

The full Maintenance table's headings, from the source, are:

| Column                        | What is shown                                                                                                                |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Province                      | Province name and realm shield/status. Loyalty is conveyed by text color and status overlays.                                |
| Level                         | Current province civilization level / source-level potential.                                                                |
| Occupied                      | Occupation status and owned-unit context; the occupied-province count is included in the expense summary.                    |
| Castle                        | Castle/tower level and a support checkbox; unchecking support reduces the displayed supported level and removes its GB cost. |
| Law / Temple / Guild / Source | The player's holding level for each type in that province; a dash/absence means no such holding.                             |
| Regency                       | RP contributed by eligible province/holding levels for the active regent.                                                    |
| Tax                           | Province plus eligible guild/temple income, initially an average projection and after collection the actual result.          |

The source sorts rows into owned provinces, foreign provinces occupied by the player, and other provinces where the player has a holding. It paginates the list. Summary values include tax collected, other income, payroll, supported castles, occupied provinces, province/holding bracket, tribute, court and total maintenance, along with current/new Treasury and unused/domain/bloodline/new Regency figures.

Province names, levels and holding values are informational in this view; the evidenced in-table edits are the castle-support checks. Taxation, occupation and payroll expose their own row-level checkboxes in their respective tabs. Right-clicking map features opens information; whether left-click selection synchronizes a map province with a table row remains unresolved.

### Six bottom controls

The six icons are confirmed by `AddDomainRegions` tooltips and callbacks, not guessed from the artwork. They are arranged as a three-by-two sprite grid (`48×46` cells):

| Position      | Control       | Action                                                                                   |
| ------------- | ------------- | ---------------------------------------------------------------------------------------- |
| Top left      | Taxation      | Opens province tax-rate and law-claim controls.                                          |
| Top middle    | Occupation    | Opens occupation, pillage and related province/holding controls.                         |
| Top right     | Payroll       | Opens per-unit GB/RP/no-pay choices.                                                     |
| Bottom left   | Maintenance   | Returns to the province maintenance table, castle-support controls and court adjustment. |
| Bottom middle | Reports       | Opens the Council/advisor reports from Realm Management.                                 |
| Bottom right  | Collect Taxes | Resolves the tax rolls; after collection, this same slot becomes **Select Actions**.     |

Additional decisions are exposed in their relevant views rather than as seven or more bottom icons: province tax rates are three checkboxes; law claims are toggles; castle support is a checkbox in each row; court uses plus/minus controls; payroll has separate pay-with-gold and pay-with-regency checks. The province rows and summary are redrawn when these choices change. Before collection, rates produce projected averages; after `Collect Taxes`, actual values are locked and the Taxation control is disabled. The help says collection iterates through the province list. `Select Actions` then leaves Maintenance for the Domain Actions screen.

Maintenance is the province/holding/asset table view, not one universal table shared by every management tab. Taxation keeps the province list but emphasizes tax-rate checkboxes, loyalty/law effects, law claims and tax projections. Occupation exposes own-occupation, pillage and foreign-holding-reduction choices, plus a loot projection. Payroll switches to unit/province rows with per-unit gold, regency and maintenance-cost columns. These views share the management/map frame and six controls while changing table columns and row actions.

The source checks projected Treasury and RP before transition; a negative balance blocks the transition so the player can revise management decisions. In the cached code, the final transition also applies pillage/holding reductions, commits the new economy for non-Basic control, and handles unpaid units. These exact finalization details are source-supported, not independently retail-verified.

## Risks and unresolved questions

1. **Double settlement:** the current PC resolver already rolls taxes/holdings, pays expenses, applies RP upkeep and records reports once at the season boundary. A future interactive Maintenance phase must partition or stage that existing resolver; it must not call a second collection/settlement.
2. **Wrong boundary:** original management precedes domain actions; HD currently settles after them. Moving the display alone would show stale balances or settle effects in the wrong order. Decide which calculations are preview-only and which are committed before integrating the screen.
3. **Loyalty and seasonal effects:** tax and occupation choices interact with loyalty, occupation maturity, sieges, seasonal spells and NPC resolution. Keep each effect at exactly one existing/approved boundary.
4. **Native units:** original source treasury is in tenths; HD runtime uses GB. Preserve raw source values and existing saved balances.
5. **Original/HD modes:** a Maintenance UI must not imply that HD Classic/Enhanced means original Basic/Advanced/Expert.
6. **Source branch defects:** law-claim logic and Basic-mode auto settlement need independent verification; source evidence must not silently become a new rule.
7. **Map/table synchronization:** active map and right-click inspection are documented; row selection/highlighting synchronization is not yet proven.
8. **Data fidelity:** keep occupation separate from sovereignty, castles separate from province ownership, source holdings separate from GB-producing holdings, and holding-only domains intact.

## Implementation status

The implementation now provides a persisted PC strategy flow of **Council → Maintenance → Collect Taxes → Select Actions → three Domain Action rounds**. Forecasts remain read-only; actual receipts, tribute and seeded income rolls are committed once by Collect Taxes; expenses, army payroll, regency, reports and delayed tax loyalty are finalized once by Select Actions. The collected income ledger is saved, and older saves without phase data migrate into their existing Actions phase without retroactive settlement. See the [settlement contract](./MAINTENANCE_SETTLEMENT_CONTRACT.md) for implementation boundaries and compatibility details.

The functional Maintenance panel occupies the left side of the strategic screen beside the active, interactive map. It provides six controls, province/taxation tables, law-claim toggles, unit payroll, individual fort-support choices where stable fortification IDs exist, court selection, income/expense/treasury/RP summaries, and manual Council reports. Province context inspection remains available alongside the table.

Own-province occupation and staged pillage controls remain explicitly unavailable because their original effects and timing are unresolved. Saves with aggregate fort levels cannot offer individual castle decisions. This work does not claim to reproduce original Basic/Advanced/Expert mode behavior or verify the final presentation manually; the full Strategic Interface milestone remains outstanding.

## Remaining reconstruction work

2. **Complete unsupported choices only with evidence.** Resolve own-occupation and pillage consequences/timing before enabling them; preserve existing HD behavior until verified.
3. **Review the functional interface.** Manually inspect the recovered-art parchment composition, six icon states, table legibility and map/context interaction at 1366×768 and larger sizes.
4. **Continue the broader strategic UI restoration separately.** Treat this Maintenance screen as a design reference and modular screen, not completion of the full interface milestone.

## Strategic UI recommendations

- Treat the Maintenance screen as a major reference for the eventual strategic interface, not as a generic modal or sidebar expansion.
- Keep the **parchment management table on the left and the interactive strategic map on the right**; the map remains central gameplay, not a decorative background.
- Prefer readable, simultaneous **tables** for provinces, holdings, armies, administration and economic values. Show comparison columns and provide contextual actions without hiding information behind nested dropdowns.
- Preserve useful current behavior: clicking a province can still expose contextual actions near that province. Reconcile it with the original parchment/map composition rather than discarding it.
- Preserve the original information hierarchy (realm/regent, loyalty and province/source levels, holdings, RP, tax, other income, payroll, maintenance, treasury) while adapting controls responsively for the 1366×768 baseline and larger viewports.
- Use recovered original UI artwork only where its identity and role are established. An asset's presence in the catalog is not evidence that it belongs on a particular screen.
